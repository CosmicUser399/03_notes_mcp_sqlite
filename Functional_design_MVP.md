# Проект: Telegram-бот заметок и напоминаний (SQLite + MCP)

## 1. Цель проекта

Разработать MVP Telegram-бота для личного хранения заметок, задач и напоминаний.

Пользователь взаимодействует с ботом преимущественно **свободным текстом**, без Reply-клавиатуры. Бот должен по смыслу сообщения определять, что именно хочет пользователь:

- сохранить заметку;
- создать задачу;
- создать напоминание о задаче/событии.

Все данные хранятся в **SQLite**.

Дополнительно необходимо разработать **MCP-сервер**, предоставляющий Cursor Composer доступ к данным SQLite через понятные инструменты. В Cursor пользователь должен иметь возможность задавать вопросы к базе обычным языком, без ручного написания SQL.

---

# 2. Роли компонентов

### Telegram-бот

Основной пользовательский интерфейс.

Отвечает за:

- приём сообщений;
- распознавание типа пользовательского запроса;
- создание и изменение заметок/задач/напоминаний;
- отображение результатов;
- отправку напоминаний пользователю;
- обработку inline-кнопок у напоминаний.

### SQLite

Единое постоянное хранилище данных MVP.

### Reminder Scheduler

Фоновый механизм, который периодически проверяет SQLite и отправляет пользователю Telegram-уведомления для наступивших напоминаний.

### MCP Server

Предоставляет Cursor набор безопасных инструментов для работы с SQLite без непосредственного ввода SQL пользователем.

### Cursor Composer

MCP-клиент.

Используется для взаимодействия с базой естественным языком, например:

- «Покажи все таблицы и их поля».
- «Выведи заметки за последние 3 дня, новые сверху».
- «Покажи напоминания на ближайшие 24 часа».
- «Найди заметки, где в заголовке есть “важно”».

Cursor не является пользовательским интерфейсом Telegram-продукта.

# 3. Основные сущности

## 3.1. Note

Обычная заметка, которую пользователь хочет сохранить.

Примеры:

- «Идея: добавить AI-рекомендации в онбординг».
- «На встрече с Иваном обсудить новый тариф».
- «Важно: клиент просил прислать презентацию до пятницы».

Минимально должна содержать:

- идентификатор;
- пользователя;
- заголовок;
- текст;
- дату создания;
- дату изменения.

Заметка не обязана иметь дату выполнения.

---

## 3.2. Task

Действие, которое пользователь должен выполнить.

Примеры:

- «Позвонить Сергею».
- «Отправить договор клиенту».
- «Купить билеты».

Минимально должна содержать:

- идентификатор;
- пользователя;
- название;
- описание при необходимости;
- статус;
- срок выполнения при наличии;
- дату создания;
- дату завершения при наличии.

Для MVP достаточно статусов:

- active / open;
- completed.

Отдельное состояние «in progress» в MVP не требуется.

---

## 3.3. Reminder

Напоминание, которое должно быть отправлено пользователю в заданный момент.

Reminder может быть связан с Task и/или представлять напоминание о произвольном событии в зависимости от выбранной модели данных.

Основной продуктовый сценарий:

> «Напомни мне завтра в 10 позвонить Сергею»

должен приводить к созданию задачи и связанного с ней напоминания.

Минимально Reminder должен иметь:

- идентификатор;
- пользователя;
- связанную сущность;
- время следующего срабатывания;
- статус;
- информацию о повторяемости при наличии.

# 4. Основной UX-принцип

Главный способ работы с ботом — **свободный естественный текст**.

Пользователь не обязан сначала выбирать тип записи.

Примеры:

> «Идея: сделать новый лендинг»

Бот определяет Note.

> «Позвонить Ивану завтра в 10»

Бот определяет Task с датой/временем.

> «Напомни завтра в 15:00 отправить договор»

Бот определяет Task + Reminder.

> «Каждый понедельник в 9 отправлять отчёт»

Бот определяет повторяющуюся Task + recurring Reminder.

Бот должен использовать контекст сообщения и семантику текста, а не только ключевые слова.

# 5. Команды Telegram

Reply-клавиатуру в MVP **не использовать**.

В меню Telegram должны быть предусмотрены следующие команды:

```text
/start
/note
/task
/reminder
/list_5
/list_10
```

## /start

Показывает приветствие и краткую инструкцию по работе с ботом.

Нужно объяснить, что пользователь может просто писать обычным текстом, а бот сам определит тип записи.

Нужно показать несколько коротких примеров.

---

## /note

Явный режим создания заметки.

Сценарий:

1. Пользователь вызывает `/note`.
2. Бот просит текст заметки.
3. Пользователь отправляет текст.
4. Бот создаёт Note.
5. Бот подтверждает сохранение.

Команда является shortcut для явного создания заметки, но не заменяет автоматическое распознавание естественного текста.

---

## /task

Явный режим создания задачи.

Сценарий:

1. Пользователь вызывает `/task`.
2. Бот просит описание задачи.
3. Пользователь вводит задачу, при необходимости со сроком.
4. Бот создаёт Task.
5. При наличии даты/времени создаётся Reminder.
6. Бот подтверждает результат.

---

## /reminder

Явный режим создания напоминания.

Сценарий:

1. Пользователь вызывает `/reminder`.
2. Бот просит указать, о чём напомнить и когда.
3. Пользователь вводит обычную фразу.
4. Бот создаёт соответствующую сущность и Reminder.
5. Бот подтверждает запланированное напоминание.

---

## /list_5

Показать 5 последних созданных записей пользователя.

Записи должны выводиться из единой хронологической ленты, независимо от типа:

- Note;
- Task;
- Reminder.

Сортировка: новые сверху.

В выдаче желательно визуально различать тип записи.

---

## /list_10

Аналогично `/list_5`, но вывести 10 последних записей.

---

# 6. Natural Language Processing / Intent Detection

MVP должен уметь определять как минимум следующие намерения:

- создать Note;
- создать Task;
- создать одноразовый Reminder;
- создать recurring Task/Reminder;
- получить данные;
- при необходимости запросить уточнение.

При неоднозначном вводе бот не должен бездумно придумывать критически важные параметры.

Пример:

> «Позвонить Андрею завтра»

Если дата понятна, но время необходимо для корректной настройки Reminder, бот должен уточнить время либо использовать явно определённое системное значение по умолчанию, если такая политика будет выбрана на этапе архитектурного проектирования.

После интерпретации бот должен подтверждать пользователю ключевые распознанные параметры.

---

# 7. Напоминания

Напоминания являются обязательной частью MVP.

Бот должен самостоятельно отправлять пользователю Telegram-сообщение, когда наступает время Reminder.

Пример:

> 🔔 Напоминание  
> Подготовить презентацию

Под сообщением должны быть inline-кнопки:

```text
✅ Готово
⏰ Напомнить позже
```

---

# 8. Snooze / «Напомнить позже»

В MVP используется понятная пользователю концепция:

**«Напомнить позже» = перенести следующее напоминание, не закрывая задачу.**

Это не начало выполнения задачи и не отдельный этап выполнения.

После нажатия на `⏰ Напомнить позже` пользователю предлагаются варианты:

```text
15 минут
1 час
3 часа
Завтра
Выбрать дату и время
```

Выбранный вариант изменяет время следующего Reminder, но не переводит Task в `completed`.

---

# 9. Завершение задачи

При нажатии:

`✅ Готово`

задача переводится в completed.

Соответствующее активное одноразовое напоминание больше не должно срабатывать.

Для recurring-задач архитектура должна учитывать дальнейшее следующее срабатывание согласно правилу повторения.

---

# 10. Повторяющиеся напоминания

MVP должен поддерживать базовые recurring reminders.

Минимальные сценарии:

- каждый день;
- каждую неделю;
- каждый месяц;
- каждый год.

Желательно поддержать естественные конструкции вида:

- «каждый понедельник в 9»;
- «каждый день в 8»;
- «1 числа каждого месяца в 10».

Сложные календарные правила могут быть оставлены за пределами MVP, если они существенно усложняют реализацию.

---

# 11. Deadline и Reminder — разные понятия

Необходимо различать:

**Deadline** — когда задача должна быть выполнена.

**Reminder** — когда бот должен уведомить пользователя.

Например:

> «Подать отчёт до пятницы. Напомни мне в среду вечером».

Модель должна позволять хранить:

```text
Task:
Подать отчёт
Deadline:
пятница

Reminder:
среда, вечер
```

Перенос Reminder через Snooze не должен автоматически менять Deadline.

---

# 12. Часовой пояс

Так как используются дата и время, пользователь должен иметь timezone.

Архитектура MVP должна предусматривать хранение timezone пользователя.

Например:

```text
Europe/Berlin
```

Интерпретация фраз вида:

> «завтра в 9»

должна выполняться относительно timezone пользователя.

Конкретный способ хранения времени (UTC/local timestamp и т. п.) определить на этапе архитектурного планирования.

---

# 13. Scheduler

Нужен отдельный фоновый механизм, который:

1. регулярно проверяет SQLite;
2. находит Reminder, время которого наступило;
3. отправляет сообщение пользователю через Telegram Bot API;
4. корректно обновляет состояние Reminder;
5. для recurring reminder рассчитывает следующее срабатывание.

Необходимо предусмотреть корректное поведение при перезапуске приложения и исключить повторную отправку одного и того же уведомления.

---

# 14. MCP

MCP Server является отдельным интерфейсом для доступа Cursor Composer к данным SQLite.

Основное требование: пользователь Cursor должен работать с данными **обычным языком, без ручного SQL**.

MCP не должен быть просто инструментом `execute_sql`, если этого можно избежать.

Предпочтительна модель специализированных инструментов.

Минимальный набор:

```text
list_tables
describe_table
list_notes
search_notes
list_tasks
list_reminders
```

При необходимости архитектура может добавить инструменты для других полезных операций.

---

# 15. Обязательные MCP-сценарии

MCP-реализация обязательно должна поддерживать следующие пользовательские запросы в Cursor Composer.

### Сценарий 1

> «Покажи все таблицы и их поля.»

Cursor должен получить через MCP список таблиц и структуру их полей без ручного SQL.

---

### Сценарий 2

> «Выведи заметки за последние 3 дня (новые сверху).»

MCP должен предоставить необходимые параметры фильтрации и сортировки.

Ожидаемая логика:

```text
entity = notes
date_from = now - 3 days
order = created_at DESC
```

---

### Сценарий 3

> «Покажи напоминания на ближайшие 24 часа.»

MCP должен вернуть Reminder, попадающие в соответствующее временное окно.

---

### Сценарий 4

> «Найди заметки, где в заголовке есть “важно”.»

MCP должен поддерживать поиск заметок по заголовку.

Поиск не должен требовать от пользователя написания SQL.

---

# 16. Безопасность MCP

MCP Server должен предоставлять только необходимые операции и не должен без необходимости раскрывать произвольное выполнение SQL.

Необходимо продумать:

- безопасную работу с параметрами запросов;
- ограничения на доступ к данным;
- корректную обработку отсутствующих таблиц/полей;
- обработку ошибок;
- отсутствие SQL injection через параметры MCP.

MCP должен работать с той же SQLite-базой, которую использует Telegram-бот.

---

# 17. Результаты работы бота

После успешного создания записи бот должен давать пользователю понятное подтверждение.

Примеры:

### Note

> ✅ Заметка сохранена  
> «Идея: добавить AI-рекомендации в онбординг»

### Task

> ✅ Задача создана  
> Позвонить Сергею  
> 📅 Завтра, 10:00

### Task + Reminder

> ✅ Задача создана  
> Позвонить Сергею  
> 🔔 Напомню завтра в 10:00

Подтверждение должно показывать основные параметры, чтобы пользователь мог быстро заметить ошибочную интерпретацию.

---

# 18. Работа с ошибками и неоднозначностью

MVP должен корректно обрабатывать:

- пустые сообщения;
- сообщения, которые не удалось классифицировать;
- отсутствующую дату;
- неоднозначное время;
- некорректную дату;
- ошибки SQLite;
- ошибки Telegram API;
- невозможность создать Reminder.

Вместо технических traceback пользователь должен получать понятное сообщение.

---

# 19. Что НЕ входит в MVP

Не требуется реализовывать:

- Reply-клавиатуру;
- web-интерфейс;
- Google Calendar;
- командную работу;
- совместные списки;
- location reminders;
- сложные права доступа;
- vector database / RAG;
- полноценный AI memory layer;
- сложные календарные recurrence rules;
- голосовые сообщения;
- отдельное состояние задачи «в работе».

Эти возможности можно рассматривать как дальнейшее развитие.

---

# 20. Критерии готовности MVP

MVP считается функционально реализованным, если выполняются следующие end-to-end сценарии.

### Telegram

Пользователь может:

1. Запустить `/start`.
2. Создать заметку обычным текстом.
3. Создать задачу обычным текстом.
4. Создать задачу с датой.
5. Создать одноразовое напоминание.
6. Создать повторяющееся напоминание.
7. Получить Telegram-уведомление в заданное время.
8. Нажать `✅ Готово`.
9. Перенести напоминание через `⏰ Напомнить позже`.
10. Посмотреть `/list_5`.
11. Посмотреть `/list_10`.
12. Использовать `/note`, `/task`, `/reminder`.

### SQLite

Все созданные данные сохраняются и корректно читаются после перезапуска приложения.

### MCP + Cursor

В Cursor Composer можно обычным языком выполнить минимум четыре обязательных сценария:

- посмотреть таблицы и поля;
- получить заметки за последние 3 дня;
- получить напоминания на ближайшие 24 часа;
- найти заметки по тексту в заголовке.

При этом пользователь не пишет SQL вручную.

# 21. Задача для Cursor Planner Agent

На основе данного функционального описания необходимо:

1. Проработать архитектуру приложения.
2. Определить технологический стек, совместимый с требованиями MVP.
3. Спроектировать структуру SQLite и связи между сущностями.
4. Определить точный контракт MCP tools.
5. Спроектировать механизм определения intent и обработки natural language.
6. Спроектировать Scheduler и надёжную обработку Reminder.
7. Продумать timezone и date/time parsing.
8. Определить структуру Telegram handlers и inline-кнопок.
9. Продумать обработку ошибок и пограничных сценариев.
10. Разбить разработку на последовательные этапы с понятными результатами каждого этапа.
11. Для каждого этапа определить изменяемые/создаваемые файлы, зависимости и критерии проверки.
12. Предложить тестовую стратегию для Telegram-функционала, SQLite, Reminder Scheduler и MCP.
13. Отдельно выделить решения, которые необходимо принять до начала реализации, если функционального описания недостаточно.

Главный приоритет MVP: **простота пользовательского взаимодействия, надёжное хранение данных, корректные напоминания и демонстрация MCP-доступа к SQLite из Cursor на естественном языке.**
